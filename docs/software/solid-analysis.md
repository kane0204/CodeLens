# SOLID 静态分析

SOLID 五项由静态分析（`POST /api/analyze`）确定性判定，无需配置模型即可运行。
AI 项目审查（`POST /api/review`）只给出可读的设计结论，不参与规则命中，也不改变发现列表。

| 原则 / 规则 | 当前检查 | 判读方式 |
|---|---|---|
| S / SRP-01 | 类直接定义的公开方法超过 12 个（排除下划线开头的方法） | 职责可能过多，需结合业务复核 |
| O / OCP-01 | 类方法内出现至少 3 种可识别的类型判断 | 条件分派可能使扩展需要修改原代码 |
| L / LSP-01 | 覆盖方法拒绝父方法接受的参数形状，改变绑定方式或同步/异步方式，或显式拒绝父类已有实现 | 报告覆盖位置、父方法位置和调用形状证据 |
| I / ISP-01 | 继承契约至少有两个公开方法，子类用直接抛出 NotImplementedError 拒绝其中成员 | 提示拆分契约，不能仅凭异常判定设计错误 |
| D / DIP-01 | 类方法直接构造至少两个已解析的项目内具体类 | 支持跨文件导入与别名；排除直接声明抽象方法的类，需复核是否确实需要注入 |

所有设计发现标记为 `inference`，并带代码位置、规则、说明和复核建议。
L/I 识别跨文件别名、单继承链，以及从 abc/typing 导入的 ABC/Protocol 标记父类。
L 不将构造器签名变化视作普通覆盖方法的替换性问题；抽象方法自身的占位抛异常也不算拒绝父类已有行为。

## 分析范围和不足

- 仅分析本次导入且解析成功的 Python 源码，不执行目标代码。
- S/O/D 是设计启发式，无法证明职责、扩展意图或依赖的业务层级。
- L 检查参数调用形状，不检查参数/返回类型兼容、前后置条件、异常集合及运行时行为；签名超过检查上限会记录覆盖缺口。
- I 检查显式拒绝接口成员，不根据客户端少用几个方法就判接口过宽；不推断动态鸭子类型接口。
- 外部或动态父类、多继承 MRO、自定义装饰器、循环继承均不猜测，记录在 `solid.coverage_gaps`。
- `solid.checked_overrides` 是已检查的覆盖方法数，不是项目符合 SOLID 的百分比。
- 补充规则最多保留 120 条发现；达到上限时 `solid.truncated` 提示可能省略发现。
- 未发现风险、没有继承关系和缺少分析证据是不同情形；均不表示已经证明符合原则。

工作台“设计检查”展示五项规则和覆盖缺口；Markdown 报告含分析边界及缺口，JSON 保留完整 `solid` 字段与发现的 `related` 父方法位置。

## 验证

```sh
python -B -m unittest discover -s tests -p 'test_*.py' -v
cd codelens-prototype && npm ci && npm run build
```

`tests/unit/test_solid.py` 覆盖正反例、签名兼容、跨文件继承、抽象契约、保守跳过、导入别名、结果稳定性与普通/AI 分析路径。
